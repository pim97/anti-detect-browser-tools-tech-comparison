## What is Patchright?

Patchright is a **patched version of Playwright** that modifies the Playwright *driver source* at build time so it stops leaving the fingerprints that give normal Playwright away. It is not a fork of Chromium and it is not a JavaScript stealth plugin — it changes how Playwright itself drives Chrome over the Chrome DevTools Protocol (CDP).

The important nuance, confirmed by reading the source: Patchright does **not** ship a patched binary of Chromium. It ships a Playwright build whose *server/client TypeScript* has been rewritten. The patches are generated by running `patchright_driver_patch.ts` against a checked-out Playwright tree using [ts-morph](https://ts-morph.com/) (an AST-manipulation library), then the result is compiled and published as the `patchright-core` and `patchright` npm packages. The Python and .NET packages are built in separate repositories on top of the `patchright-core` npm package (PyPI; NuGet through a manually triggered publish step). You install `patchright` instead of `playwright` and keep your existing Playwright code.

> **Note:** Patchright only patches **Chromium-based** browsers. Firefox and WebKit are explicitly unsupported (the stealth patches are Chromium/CDP-specific).

## How It Works

### The Core Problem with Playwright

Standard Playwright is detectable because of *how it talks to Chrome*, independent of any fingerprint spoofing. The README names a Runtime leak and a Console leak (**Tier B**); the driver source removes the first one directly (**Tier A**):

```javascript
// Enabling the Runtime domain is observable from inside the page
// (the classic aslushnikov "Runtime.enable" leak) — anti-bots probe for it.
await client.send('Runtime.enable');
```

The README's second named leak is `Console.enable`; no driver patch module references that call (see section 2 below). The README also lists command-line flags (`--enable-automation`) and `navigator.webdriver` as detection points; init-script and binding handling is covered in sections 1 and 3.

### Patchright's Solution

Patchright applies a large stack of source patches — **34 driver-side patch modules** (in `driver_patches/`, 5,091 lines of TypeScript) plus **ten client-side patch modules** carried in the `patchright-nodejs` submodule, plus five protocol-spec (`*.yml`) mutations. The generated `patchright.patch` is 50,211 lines (99 per-file diffs, +20,568 / −10,826). Its 44 `playwright-core` file diffs appear twice, once under `node_modules/playwright-core/src/` and once under `packages/playwright-core/src/`, with the same changed lines, so about 9,800 of the added lines repeat an earlier hunk. The key mechanisms:

#### 1. Runtime.enable Bypass (the biggest patch)

The project calls this "the biggest Patch Patchright uses." Instead of enabling the `Runtime` CDP domain, Patchright executes JavaScript inside **isolated execution contexts** it manages by hand.

**Traditional Playwright:**
```javascript
await client.send('Runtime.enable');  // Detectable!
```

**Patchright:**
- Removes the `Runtime.enable` sends from the patched driver (**Tier A**): `crPagePatch.ts:153` (the `FrameSession._initialize` promise list, together with the `Runtime.addBinding` call for Playwright's own binding) and `:463-469` (`_onAttachedToTarget`), `crDevToolsPatch.ts:22-28` and `crServiceWorkerPatch.ts:31-34`.
- Removes Playwright's own isolated-world bootstrap and rebuilds context handling manually. In `crPagePatch.ts` the patch *strips out* the original `Page.createIsolatedWorld` loop and re-inserts its own logic that resolves the `"utility"` context lazily and re-evaluates page bindings per frame:

  ```javascript
  // driver_patches/crPagePatch.ts:211-218 — logic inserted into the non-initial-page branch (template text from the AST edit)
  const localFrames = this._isMainFrame()
    ? this._page.frames()
    : [this._page.frameManager.frame(this._targetId)!];
  for (const frame of localFrames) {
    this._page.frameManager.frame(frame._id)._context("utility").catch(() => {});
    for (const binding of this._crPage._browserContext._pageBindings.values())
      frame.evaluateExpression(binding.source).catch(e => {});
  }
  ```
- `framesPatch.ts:211-310` replaces `Frame.context()` with a lazy `_context(world)`: the main-world context id comes from `Runtime.evaluate("globalThis")` with `serializationOptions: { serialization: "idOnly" }` and is parsed out of the returned `objectId` (l.256-265); an iframe's main world is resolved through `DOM.getFrameOwner` → `DOM.describeNode` → `DOM.resolveNode` (l.183-210); the isolated world is created on first use with `Page.createIsolatedWorld` (l.281). Since `88cf0a0` these lookups are cached per frame as promises (`_mainWorldContextPromise` and siblings).
- Adds an `isolatedContext?: boolean` parameter throughout the evaluate chain (`server/javascript.ts`, `frameSelectors.ts`, and the `frame.yml` / `handles.yml` / `worker.yml` protocol specs) so callers can choose the **Main** or **Isolated** world. The "choose execution context (Main/Isolated)" TODO is now done. On the client side the parameter defaults to `true` (`patchright-nodejs` `client_patches/pagePatch.ts:54,76`; an `isolated_context` keyword with default `True` in the Python wrapper), so `page.evaluate()` runs in the isolated world unless `false` is passed; the READMEs state the same default.
- `crExecutionContextPatch.ts` (new since the previous verification) adds `CRExecutionContext.findFunctions` (l.13-81), which finds the `callbackBridge` function objects of bindings created with `noGlobal` through `Runtime.evaluate`, `Runtime.getProperties` and `Runtime.queryObjects`; `utilityScriptPatch.ts` adds the matching `takeFunctionCallback` hook and `javascriptPatch.ts:10-35` the `ExecutionContext.findFunctions` entry point.

#### 2. Console.enable Bypass — by disabling the Console API entirely

The README says Patchright patches the Console leak by **disabling the Console API altogether** (**Tier B**). In the source, no driver patch module references `Console.enable` (**Tier A**: search of `driver_patches/` and of the generated `patchright.patch`); the Console effect appears to follow from the Runtime-domain removal in section 1 (inference, not tested here). The driver's CI is consistent with that: `utils/modify_tests.ts` skips upstream console-dependent tests with the reason that the Console CDP domain is disabled, and `utils/detection_smoke_test.mjs` asserts that logging an `Error` whose `stack` is a getter causes no `stack` reads. The practical cost: `console.log()` and friends are effectively dead inside a Patchright browser. The README's guidance is to use JavaScript loggers if you must (while noting those, too, can be detected).

#### 3. Init-Script Injection (README: Playwright Routes instead of CDP)

The README (**Tier B**) says that, to run init scripts without `Runtime.enable`, Patchright injects JavaScript into HTML responses through **Playwright Routes** rather than a CDP `addScriptToEvaluateOnNewDocument` call. What the source contains (**Tier A**, read at `26ab9ae`, not executed):

- **Client side** (`patchright-nodejs` `client_patches/pagePatch.ts:27-47`, `browserContextPatch.ts:27-47`): `addInitScript`, `exposeBinding` and `exposeFunction` first call `installInjectRoute()`, which registers a `**/*` route that calls `route.fallback({ patchrightInitScript: true })` for `http(s)` document requests (the flag is carried through the `network.yml` protocol spec).
- **Server side** (`crNetworkManagerPatch.ts`): `RouteImpl.continue` with that flag sends `Fetch.continueRequest` with `interceptResponse: true` (l.534-560); the response-stage event reads the body with `Fetch.getResponseBody` and calls `fulfill` (l.562-600). `fulfill` (l.391-496) can insert one self-removing `<script>` per init script into the `<head>`, and rewrites `content-security-policy` / `-report-only` response headers and `<meta http-equiv="Content-Security-Policy">` tags through `_fixCSP` (l.198-310). `_fixCSP` adds the nonce found in the existing CSP (or `'unsafe-inline'` when there is none), `'unsafe-eval'` and a wildcard source to `script-src` and relaxes `style-src`, `img-src` / `font-src`, `connect-src` and `frame-ancestors`.
- **What feeds `fulfill`:** it builds the `<script>` tags from `_mainFrameSession._evaluateOnNewDocumentScripts` (l.397-402) and injects nothing when that list is empty. At `88cf0a0` the patched `FrameSession._evaluateOnNewDocument` appended every init script to that list *and* called CDP `Page.addScriptToEvaluateOnNewDocument`. At `26ab9ae` (since commit `e8295b9`, 2026-08-17) `crPagePatch.ts:503-507` only makes the CDP call, and a search of `driver_patches/`, the generated `patchright.patch` and the three wrapper repositories finds no other code that adds to the list. Read from source, the route-injection branch therefore has nothing to inject at this commit, and context- and page-level init scripts (`crPagePatch.ts:244-250`) and bindings (`crPagePatch.ts:299`, with `runImmediately`) are registered through `Page.addScriptToEvaluateOnNewDocument`. The README text did not change. No runtime test was run here, so the behaviour of the published packages is unconfirmed (**Tier D**).

```html
<!-- Template built by fulfill() (crNetworkManagerPatch.ts:473-477) -->
<script class="<initScriptTag>" nonce="..." id="randomId" type="text/javascript">
  document.getElementById("randomId")?.remove();  // self-delete
  /* init script source */
</script>
```

> **Project-stated caveat (README, Tier B):** route-based injection can trip the same edge cases any Playwright Route can, and the injected init scripts are theoretically detectable by timing attacks. The maintainers state that no current anti-bot checks for that timing side-channel and rate the risk low. The driver's own test skip list (`utils/modify_tests.ts`, **Tier A**) additionally records that route-injected init scripts cannot affect `about:blank` / `data:` pages and that CSP restrictions are intentionally relaxed for injected scripts.

#### 4. Command-Line Flag Sanitization

`chromiumSwitchesPatch.ts` (l.22-45) rewrites Playwright's default Chromium switches. Verified against source, it **removes** the following flags (the README highlights the first five):

- `--enable-automation` (the `assistantMode ? '' : '--enable-automation'` entry is removed — `navigator.webdriver` tell)
- `--disable-popup-blocking`
- `--disable-component-update` (removed so the browser doesn't look like a stealth driver)
- `--disable-default-apps`
- `--disable-extensions` (removed so extensions work)
- `--disable-client-side-phishing-detection`
- `--disable-component-extensions-with-background-pages`
- `--allow-pre-commit-input`
- `--disable-ipc-flooding-protection`
- `--metrics-recording-only`
- `--unsafely-disable-devtools-self-xss-warnings`
- `--disable-back-forward-cache`
- the big `--disable-features=...` blob (ImprovedCookieControls, LazyFrameLoading, AcceptCHFrame, HttpsUpgrades, PaintHolding, etc.)

and **adds**:

- `--disable-blink-features=AutomationControlled` (README: avoids `navigator.webdriver` detection)

`chromiumPatch.ts:15-32` additionally makes `--headless=new` unconditional (it replaces the `PLAYWRIGHT_CHROMIUM_USE_HEADLESS_NEW` branches) and drops `--enable-unsafe-swiftshader` from the default arguments.

#### 5. Closed Shadow Root & XPath Access

`frameSelectorsPatch.ts` + `XPathSelectorEnginePatch.ts` let ordinary Playwright locators reach into **closed** shadow roots (which normal Playwright cannot), including **XPath selectors inside closed shadow roots**. You just use normal locators; the patch resolves the piercing internally. Per source: `frameSelectorsPatch.ts` adds `_hasClosedShadowRoots()` (a `DOM.getDocument` call with `depth: -1, pierce: true`, l.33-48) and finds closed roots through `DOM.describeNode` with `pierce: true` and `DOM.resolveNode` (l.274-323); for XPath, `XPathSelectorEnginePatch.ts:17-55` parses a shadow root's `innerHTML` with `DOMParser`, evaluates the expression against that copy and maps the matches back to the live elements by position. `utils/custom_tests/closed-shadow-root.spec.ts` (new since the previous verification) is one of three project-specific specs that `utils/modify_tests.ts` copies into the Playwright test tree.

#### 6. CLI Aliasing

`cliAliasPatch.ts` string-replaces "Playwright" with "Patchright" in the CLI help text and messages (`cli/program.ts`, `cli/programWithTestStub.ts`, `server/android/android.ts`, `server/registry/index.ts`), so `patchright install chromium`, `patchright version`, etc. print Patchright branding. The `patchright` command name itself comes from the package build: the npm `bin` entry set in `patchright-nodejs/patchright_rebranding.ts:197-198`, and a `patchright` console script (replacing `playwright`) in the Python build (`patch_python_package.py:98-99`).

## Usage Example

Patchright is a drop-in replacement — change the import, keep the code.

### Python
```python
from patchright.sync_api import sync_playwright

with sync_playwright() as p:
    # README "Best Practice": launch_persistent_context(user_data_dir, channel="chrome",
    # headless=False, no_viewport=True) and no custom UA / headers.
    browser = p.chromium.launch(headless=False)
    page = browser.new_page()
    page.goto("https://bot.sannysoft.com")
    browser.close()
```

### Node.js
```javascript
const { chromium } = require('patchright');

(async () => {
    const browser = await chromium.launch({ headless: false });
    const page = await browser.newPage();
    await page.goto('https://bot.sannysoft.com');
    await browser.close();
})();
```

> Remember: `console.log` inside the page will not surface (Console API disabled). Use external logging.

## Pros and Cons

### Advantages

| Advantage | Description |
|---|---|
| CDP-level changes | Removes the `Runtime.enable` sends and the listed Chromium flags in the driver source rather than injecting JS on top of it |
| Drop-in Playwright API | Full Playwright API; change the import and you're done |
| Auto-tracks Playwright | An hourly workflow releases when a new upstream Playwright tag appears and the test run passes |
| Multi-language | Python, Node.js, and community .NET packages; all three repositories have commits after 2026-08-14 |
| Closed shadow-root + XPath | Reaches elements normal Playwright cannot |
| `patchright` CLI | CLI text rebranded; the `patchright` command name is set in the package build |
| Open source, Apache 2.0 | Every patch is a readable `.ts` file; the full generated diff ships as `patchright.patch` |

### Limitations

| Limitation | Description |
|---|---|
| No console output | `console.log()` doesn't work (Console API disabled by design) |
| Chromium only | Firefox / WebKit unsupported |
| No fingerprint spoofing | No canvas/WebGL/audio/screen spoofing or fingerprint rotation (no module in `driver_patches/` touches them) |
| No TLS/JA3 impersonation | Uses real Chromium's network stack; no curl_cffi-style impersonation |
| Init-script timing leak | README: route-injected init scripts are theoretically timing-detectable (project-rated low risk); section 3 describes what the current source does |
| Route side-effects | `installInjectRoute()` registers a `**/*` route once `addInitScript`, `exposeBinding` or `exposeFunction` is used; README: Route-related quirks can appear |
| Some Playwright tests fail | Passes most but not all upstream tests; a few bugs are deemed unfixable/irrelevant (see issue #30); `utils/modify_tests.ts` holds a per-test skip list with reasons |
| Isolated-world `evaluate` default | `evaluate` / `evaluateHandle` default to `isolatedContext = true` (client patches), so page globals are not visible unless `false` is passed; `modify_tests.ts` records evaluate-argument and global-visibility differences |
| "Undetectable" is the project's framing | The mechanism is CDP-tell removal; it addresses Layer 1 only |

## Technical Architecture

### How the patch is produced

```
patchright_driver_patch.ts        # orchestrator: runs every patch against a Playwright checkout
   ├── driver_patches/*.ts        # 34 SERVER-side patch modules (ts-morph AST edits)
   ├── patchright-nodejs/ (submodule)  # 10 CLIENT-side patch modules (browserContext, clientHelper, clock, frame, jsHandle, locator, network, page, tracing, worker)
   └── protocol/spec/*.yml         # 5 YAML mutations (adds isolatedContext / patchrightInitScript / focusControl params)
                    │
                    ▼
             ts-morph applies AST edits + YAML edits
                    │
                    ▼
             patched Playwright  →  npm run build  →  rebranded patchright-core / patchright npm packages
             (patchright.patch is a generated diff kept as documentation only)
```

### The 34 driver patch modules (`driver_patches/index.ts`)

```
browserContextDispatcherPatch   crNetworkManagerPatch     pageBindingPatch
browserContextPatch             crPagePatch               pageDispatcherPatch
buildPatch                      crServiceWorkerPatch      pagePatch
chromiumPatch                   frameDispatcherPatch      recorderPatch
chromiumSwitchesPatch           frameSelectorsPatch       screenshotterPatch
cliAliasPatch                   framesPatch               snapshotterInjectedPatch
clockPatch                      javascriptPatch           snapshotterPatch
crBrowserPatch                  jsHandleDispatcherPatch   tracingPatch
crCoveragePatch                 launchAppPatch            utilityScriptPatch
crDevToolsPatch                 networkDispatchersPatch   utilityScriptSerializersPatch
crExecutionContextPatch         networkPatch              XPathSelectorEnginePatch
credentialsPatch
```

The heaviest modules by size: `framesPatch.ts` (~56 KB — the `Runtime.enable` avoidance and context management), `crNetworkManagerPatch.ts` (~23 KB — network interception, route fulfilment and CSP rewriting), `crPagePatch.ts` (~22 KB — script injection & bindings), `frameSelectorsPatch.ts` (~18 KB — shadow-root piercing), `utilityScriptSerializersPatch.ts` (~14 KB). `driver_patches/` contains 36 files: the 34 modules plus `index.ts` and `utils.ts`.

### Build Process

1. `.github/workflows/patchright_release.yml` runs hourly and on manual dispatch. `utils/release_version_check.sh` compares the latest `microsoft/playwright` release tag with the release tags of this repository and proceeds when the Playwright tag has no matching release.
2. It clones `microsoft/playwright` at that tag (`git clone ... --branch <tag>`, then `npm ci`) and updates the `patchright-nodejs` submodule — the only submodule — for the client patches.
3. Before anything is published, `patchright_tests.yml` applies the patches, builds, installs Chromium and Chrome, and runs `utils/detection_smoke_test.mjs` (asserts that `navigator.webdriver` is not `true`, that no `__pw*` / `__playwright*` globals exist, and that console serialization does not read `Error.stack`, in the main page, an iframe and a popup), then Playwright's own `chromium-page` and `chromium-library` test projects with the per-test skip list in `utils/modify_tests.ts` and three project-specific specs in `utils/custom_tests/`. After the tests, whatever their outcome (`if: always()`), `check_patch_impact.yml` (`utils/check_patch_impact.ts`) compares the old and new Playwright tags through the GitHub API, classifies each patched symbol as signature changed / body changed / removed / added / unchanged, and writes `report.json`, a step summary and an affected-diff artifact. A test failure opens a "Release Failed" issue (with that report) and a draft fix PR and skips publishing.
4. On success the workflow runs `npm run patch` (applies `patchright_driver_patch.ts`), Playwright's `generate_channels.js` and `npm run build`; `patchright_rebranding.ts` then renames the packages, and `patchright-core` and `patchright` are published to npm with provenance. A GitHub release named after the Playwright tag is then created (e.g. **v1.63.0**, September 2026).
5. Since commit `e8295b9` (2026-08-17) the driver is no longer built as per-platform zip bundles for GitHub releases (`utils/release_driver.sh` was deleted); the Python and .NET wrappers take it from the `patchright-core` npm package instead (see below).
6. `patch_file_updater.yml` regenerates `patchright.patch` on pushes to `main` (`diff -ruN -x protocol.yml --minimal` between an unpatched and a patched Playwright clone); the file's own header says it is documentation and is not used to patch.
7. When Playwright's codebase shifts, fixes can take a few days (README).

Toolchain (from `package.json`, current): ts-morph ^27, TypeScript ^6, Biome ^2.4, `yaml` ^2.7, tsx ^4.21.

## When to Use Patchright

### Best For:
- Sites where the *automation protocol* is the tell (Runtime.enable / Console.enable / flag probes)
- Projects already on Playwright that want stealth with zero code changes
- Chromium automation needing the full Playwright API (routes, tracing, locators, etc.)
- Reaching into closed shadow roots / XPath that vanilla Playwright can't

### Not Ideal For:
- Simple HTML scraping (a real browser is overkill — see Scrapling's HTTP tier)
- Anything needing `console.log` debugging inside the page
- Firefox or WebKit automation
- Cases needing **fingerprint rotation**, **canvas/WebGL/audio spoofing** or **TLS/JA3 impersonation** (none is implemented in the driver source)
- Trusted-input requirements (the README pairs Patchright with CDP-Patches for Brotector; see Related Projects)

## Summary

Patchright is a **CDP-tell-removal layer** for Playwright. It rewrites the Playwright driver source (34 driver-side patch modules + 10 client patch modules + protocol edits; TypeScript, Apache-2.0) so the browser stops advertising the signals the README names: `Runtime.enable`, the Console API, the `--enable-automation` flag, and init-script/binding artifacts. It also adds closed shadow-root/XPath access and a `patchright` command name.

What it does not implement: fingerprint spoofing, TLS impersonation, or an input motion model. It ships no canvas/WebGL/audio spoofing and no fingerprint rotation (no module in `driver_patches/` touches them); the README states that route-based init injection can be detected by timing attacks (rated low risk by the maintainers; section 3 describes what the current source does); and Console output is unavailable by design. The README pairs it with CDP-Patches for Brotector.

As of 2026-09-30 (verified against `26ab9ae`): version 1.63.0 tracking Playwright 1.63.0 (GitHub release 2026-09-08, npm the same day, PyPI 2026-09-20), repo last pushed 2026-09-13, 40 contributors, 5 open issues, 4,720 stars, and a per-release test run against the Playwright suite before publishing. Since the previous verification (2026-08-14, `88cf0a0`) the driver moved from 1.61.1 to 1.63.0 (the history includes fixes for the Playwright 1.62.1 and 1.63.0 release failures), `driver_patches/` grew from 32 to 34 modules, driver distribution moved from per-platform zip bundles to the `patchright-core` npm package, and the init-script registration in `crPagePatch.ts` changed (section 3).

**Evidence:** Tier A for the driver patch mechanics above; Tier B for the anti-bot service list; no independent detection measurements (see [METHODOLOGY.md](METHODOLOGY.md)).

**Complexity:** Low — drop-in Playwright replacement.

**Applicability:** Chromium automation where the CDP automation signature is the detection vector. Verified scope: an AST rewrite of the Playwright driver that avoids `Runtime.enable` by executing JS in isolated contexts, at the cost of the Console API. It implements no fingerprint spoofing (Layer 2), no TLS impersonation (Layer 4), and no input motion model (Layer 3) — the project pairs with the separate CDP-Patches library for trusted input.
