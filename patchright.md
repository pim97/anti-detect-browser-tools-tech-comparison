## What is Patchright?

Patchright is a **patched version of Playwright** that modifies the Playwright *driver source* at build time so it stops leaving the fingerprints that give normal Playwright away. It is not a fork of Chromium and it is not a JavaScript stealth plugin — it changes how Playwright itself drives Chrome over the Chrome DevTools Protocol (CDP).

The important nuance, confirmed by reading the source: Patchright does **not** ship a patched binary of Chromium. It ships a Playwright build whose *server/client TypeScript* has been rewritten. The patches are generated by running `patchright_driver_patch.ts` against a checked-out Playwright tree using [ts-morph](https://ts-morph.com/) (an AST-manipulation library), then the result is compiled and published to PyPI, npm, and NuGet. You install `patchright` instead of `playwright` and keep your existing Playwright code.

> **Note:** Patchright only patches **Chromium-based** browsers. Firefox and WebKit are explicitly unsupported (the stealth patches are Chromium/CDP-specific).

## How It Works

### The Core Problem with Playwright

Standard Playwright is detectable because of *how it talks to Chrome*, independent of any fingerprint spoofing. The two headline tells:

```javascript
// Enabling the Runtime domain is observable from inside the page
// (the classic aslushnikov "Runtime.enable" leak) — anti-bots probe for it.
await client.send('Runtime.enable');

// The Console domain is similarly observable.
await client.send('Console.enable');
```

Detection scripts also look at command-line flags (`--enable-automation`), the `navigator.webdriver` flag, and artifacts left by how init scripts and bindings are injected.

### Patchright's Solution

Patchright applies a large stack of source patches — **30 driver-side patch modules** (in `driver_patches/`) plus a set of client-side patches carried in the `patchright-nodejs` submodule, plus five protocol-spec (`*.yml`) mutations. Together they add up to **~5,928 inserted lines** in the generated `patchright.patch` (11,635 lines total including context/removals). The key mechanisms:

#### 1. Runtime.enable Bypass (the biggest patch)

The project calls this "the biggest Patch Patchright uses." Instead of enabling the `Runtime` CDP domain, Patchright executes JavaScript inside **isolated execution contexts** it manages by hand.

**Traditional Playwright:**
```javascript
await client.send('Runtime.enable');  // Detectable!
```

**Patchright:**
- Never calls `Runtime.enable`.
- Removes Playwright's own isolated-world bootstrap and rebuilds context handling manually. In `crPagePatch.ts` the patch *strips out* the original `Page.createIsolatedWorld` loop and re-inserts its own logic that resolves the `"utility"` context lazily and re-evaluates page bindings per frame:

  ```javascript
  // driver_patches/crPagePatch.ts — re-inserted logic (paraphrased from AST edit)
  const localFrames = this._isMainFrame()
    ? this._page.frames()
    : [this._page.frameManager.frame(this._targetId)!];
  for (const frame of localFrames) {
    this._page.frameManager.frame(frame._id)._context("utility").catch(() => {});
    for (const binding of this._crPage._browserContext._pageBindings.values())
      frame.evaluateExpression(binding.source).catch(e => {});
  }
  ```
- Adds an `isolatedContext?: boolean` parameter throughout the evaluate chain (`server/javascript.ts`, `frameSelectors.ts`, and the `frame.yml` / `handles.yml` / `worker.yml` protocol specs) so callers can choose the **Main** or **Isolated** world. The "choose execution context (Main/Isolated)" TODO is now done.

#### 2. Console.enable Bypass — by disabling the Console API entirely

Patchright avoids the `Console.enable` leak by **not enabling the Console domain at all**. The practical cost: `console.log()` and friends are effectively dead inside a Patchright browser. The project's own guidance is to use JavaScript loggers if you must (while noting those, too, are detectable).

#### 3. Init-Script Injection via Playwright Routes (not CDP)

To run init scripts without `Runtime.enable`, Patchright injects JavaScript into HTML responses using **Playwright Routes** rather than a CDP `addScriptToEvaluateOnNewDocument` call. `crNetworkManagerPatch.ts` handles the network layer: it can rewrite `content-security-policy` / `content-security-policy-report-only` **response headers** and strip `<meta http-equiv="Content-Security-Policy">` tags so an injected inline `<script>` isn't blocked.

```html
<!-- Injected into the HTML response body via a route, not via CDP -->
<script nonce="..." id="randomId">
  document.getElementById("randomId")?.remove();  // self-delete
  /* injected init code */
</script>
```

> **Honest caveat (stated by the project):** this route-based injection can trip the same edge cases any Playwright Route can, and the injected init scripts are **theoretically detectable by timing attacks**. The maintainers argue no current anti-bot checks for that specific timing side-channel, so they rate the risk low — but it is a real, acknowledged leak, not a solved problem.

#### 4. Command-Line Flag Sanitization

`chromiumSwitchesPatch.ts` rewrites Playwright's default Chromium switches. Verified against source, it **removes** a substantial list of automation-revealing / stealth-revealing flags:

- `--enable-automation` (removed for normal launches — `navigator.webdriver` tell)
- `--disable-popup-blocking`
- `--disable-component-update` (removed so the browser doesn't look like a stealth driver)
- `--disable-default-apps`
- `--disable-extensions` (removed so extensions work)
- `--disable-client-side-phishing-detection`
- `--disable-component-extensions-with-background-pages`
- `--allow-pre-commit-input`
- `--disable-ipc-flooding-protection`
- `--metrics-recording-only`
- `--unsafely-disable-devtools-self-xss-warnings`
- `--disable-back-forward-cache`
- the big `--disable-features=...` blob (ImprovedCookieControls, LazyFrameLoading, AcceptCHFrame, HttpsUpgrades, PaintHolding, etc.)

and **adds**:

- `--disable-blink-features=AutomationControlled` (kills `navigator.webdriver`)

#### 5. Closed Shadow Root & XPath Access

`frameSelectorsPatch.ts` + `XPathSelectorEnginePatch.ts` let ordinary Playwright locators reach into **closed** shadow roots (which normal Playwright cannot), including **XPath selectors inside closed shadow roots**. You just use normal locators; the patch resolves the piercing internally.

#### 6. CLI Aliasing

`cliAliasPatch.ts` rewrites the Playwright CLI so a first-class **`patchright`** command exists — `patchright install chromium`, `patchright version`, etc. — with the help text/branding swapped from "Playwright" to "Patchright." (Not present in older versions of this analysis.)

## Detection Vectors Bypassed

| Detection Method | How Patchright Defeats It | Source |
|---|---|---|
| `navigator.webdriver` | `--disable-blink-features=AutomationControlled` added, `--enable-automation` removed | `chromiumSwitchesPatch.ts` |
| `Runtime.enable` timing/probe | Never enabled — manual isolated-context management | `crPagePatch.ts`, `framesPatch.ts`, `javascriptPatch.ts` |
| `Console.enable` probe | Console domain never enabled (API disabled) | driver patches |
| Init-script fingerprinting | Injected into HTML via Routes, self-deleting `<script>` | `crNetworkManagerPatch.ts` |
| CSP blocking injected scripts | CSP response headers + `<meta>` CSP stripped | `crNetworkManagerPatch.ts` |
| Stealth-driver flag tells | `--disable-component-update` etc. removed | `chromiumSwitchesPatch.ts` |
| Closed shadow-root probes | Locators/XPath pierce closed shadow roots | `frameSelectorsPatch.ts`, `XPathSelectorEnginePatch.ts` |

## Usage Example

Patchright is a drop-in replacement — change the import, keep the code.

### Python
```python
from patchright.sync_api import sync_playwright

with sync_playwright() as p:
    # Best stealth: use a persistent context + the "chromium" channel,
    # no custom UA / headers. See project docs for the recommended setup.
    browser = p.chromium.launch(headless=False)
    page = browser.new_page()
    page.goto("https://bot.sannysoft.com")
    browser.close()
```

### Node.js
```javascript
const { chromium } = require('patchright');

(async () => {
    const browser = await chromium.launch({ headless: false });
    const page = await browser.newPage();
    await page.goto('https://bot.sannysoft.com');
    await browser.close();
})();
```

> Remember: `console.log` inside the page will not surface (Console API disabled). Use external logging.

## Pros and Cons

### Advantages

| Advantage | Description |
|---|---|
| CDP-level stealth | Removes `Runtime.enable` / `Console.enable` / flag tells at the driver, not on top of it |
| Drop-in Playwright API | Full Playwright API; change the import and you're done |
| Auto-tracks Playwright | Deployment is automated on every upstream Playwright release |
| Multi-language | Python, Node.js, and community .NET packages, all currently maintained |
| Closed shadow-root + XPath | Reaches elements normal Playwright cannot |
| `patchright` CLI | First-class CLI alias for install/version/etc. |
| Open source, Apache 2.0 | Every patch is a readable `.ts` file; the full generated diff ships as `patchright.patch` |

### Limitations

| Limitation | Description |
|---|---|
| No console output | `console.log()` doesn't work (Console API disabled by design) |
| Chromium only | Firefox / WebKit unsupported |
| No fingerprint spoofing | No canvas/WebGL/audio/screen spoofing or fingerprint rotation — pair with Camoufox/CDP-Patches for that |
| No TLS/JA3 impersonation | Uses real Chromium's network stack; no curl_cffi-style impersonation |
| Init-script timing leak | Route-injected init scripts are theoretically timing-detectable (project-acknowledged, rated low risk) |
| Route side-effects | Because init scripts use Playwright Routes, any Route-related quirks can appear |
| Some Playwright tests fail | Passes most but not all upstream tests; a few bugs are deemed unfixable/irrelevant (see issue #30) |
| "Undetectable" is the project's framing | The mechanism is CDP-tell removal; it addresses Layer 1 only |

## Technical Architecture

### How the patch is produced

```
patchright_driver_patch.ts        # orchestrator: runs every patch against a Playwright checkout
   ├── driver_patches/*.ts        # 30 SERVER-side patch modules (ts-morph AST edits)
   ├── patchright-nodejs/ (submodule)  # CLIENT-side patches (browserContext, frame, page, network, worker, clock, ...)
   └── protocol/spec/*.yml         # 5 YAML mutations (adds isolatedContext / patchrightInitScript / focusControl params)
                    │
                    ▼
             ts-morph applies AST edits + YAML edits
                    │
                    ▼
             patchright.patch  (~5,928 added lines)  →  compiled  →  PyPI / npm / NuGet
```

### The 30 driver patch modules (`driver_patches/index.ts`)

```
browserContextDispatcherPatch   crServiceWorkerPatch     pageBindingPatch
browserContextPatch             credentialsPatch         pageDispatcherPatch
chromiumPatch                   crNetworkManagerPatch    pagePatch
chromiumSwitchesPatch           crPagePatch              recorderPatch
cliAliasPatch                   frameDispatcherPatch     screenshotterPatch
clockPatch                      frameSelectorsPatch      snapshotterInjectedPatch
crBrowserPatch                  framesPatch              snapshotterPatch
crCoveragePatch                 javascriptPatch          tracingPatch
crDevToolsPatch                 jsHandleDispatcherPatch  utilityScriptSerializersPatch
                                launchAppPatch           XPathSelectorEnginePatch
                                networkDispatchersPatch
```

The heaviest modules by size: `framesPatch.ts` (~54 KB — the Runtime.enable avoidance), `crPagePatch.ts` (~22 KB — script injection & bindings), `crNetworkManagerPatch.ts` (~20 KB — network interception & CSP), `frameSelectorsPatch.ts` (~15 KB — shadow-root piercing), `utilityScriptSerializersPatch.ts` (~10 KB).

### Build Process

1. A GitHub Action watches for new `microsoft/playwright` releases.
2. It checks out the matching Playwright source (as a submodule).
3. `patchright_driver_patch.ts` applies all patches via ts-morph (+ YAML edits).
4. The result is built and published to GitHub Releases, PyPI, npm, and NuGet — versioned to match Playwright (e.g. driver **v1.61.1**, June 2026).
5. Since a recent addition, every release is run against the **Playwright test suite** to catch upstream breakage. When Playwright's codebase shifts, fixes can take a few days.

Toolchain (from `package.json`, current): ts-morph ^27, TypeScript ^6, Biome ^2.4, `yaml` ^2.7, tsx ^4.21.

## When to Use Patchright

### Best For:
- Sites where the *automation protocol* is the tell (Runtime.enable / Console.enable / flag probes)
- Projects already on Playwright that want stealth with zero code changes
- Chromium automation needing the full Playwright API (routes, tracing, locators, etc.)
- Reaching into closed shadow roots / XPath that vanilla Playwright can't

### Not Ideal For:
- Simple HTML scraping (a real browser is overkill — see Scrapling's HTTP tier)
- Anything needing `console.log` debugging inside the page
- Firefox or WebKit automation
- Cases needing **fingerprint rotation** or **canvas/WebGL/audio spoofing** (pair with Camoufox) or **TLS/JA3 impersonation** (pair with an impersonating HTTP client)
- Behavioral/trusted-input requirements without the companion CDP-Patches library

## Summary

Patchright is a **CDP-tell-removal layer** for Playwright. It rewrites the Playwright driver source (30 driver-side patch modules + client patches + protocol edits, ~5,928 added lines, all Apache-2.0 and readable) so the browser stops advertising the classic automation signals: `Runtime.enable`, `Console.enable`, the `--enable-automation` flag, and init-script/binding artifacts. It adds real conveniences too — closed shadow-root/XPath access and a first-class `patchright` CLI.

What it is **not**: a fingerprint spoofer, a TLS impersonator, or a magic "undetectable" button. It ships no canvas/WebGL/audio spoofing and no fingerprint rotation, its route-based init injection carries an acknowledged (if low-risk) timing leak, and Console output is sacrificed by design. On serious targets you pair it with residential proxies and often with CDP-Patches (input) and/or Camoufox (fingerprints).

The project is **healthy and current as of 2026-08-14**: version 1.61.x tracking Playwright 1.61.1, driver release June 2026 with the repo pushed 2026-08-05, Python and .NET packages updated through August, 40 contributors, only 7 open issues, and automated per-release testing against the Playwright suite. Note that the *published version* has been static since July while development continued — an unchanged version number here reflects Playwright not having shipped a new release to track, not a stalled project.

**Effectiveness Rating:** High for protocol-level stealth (with proxies + companion tooling); not a standalone fingerprint solution.

**Complexity:** Low — drop-in Playwright replacement.

**Applicability:** Chromium automation where the CDP automation signature is the detection vector. Verified scope: an AST rewrite of the Playwright driver that avoids `Runtime.enable` by executing JS in isolated contexts, at the cost of the Console API. It implements no fingerprint spoofing (Layer 2), no TLS impersonation (Layer 4), and no input motion model (Layer 3) — the project pairs with the separate CDP-Patches library for trusted input.
